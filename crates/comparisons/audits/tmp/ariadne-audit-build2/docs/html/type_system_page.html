Types and Concepts

Representations

Objects from discrete mathematics, such as integers and rational numbers, can be described by a finite amount of data. (This holds even if the sets themselves are infinite, though we then need an arbitrarily large amount of data to store objects.) We can think of this data as a word over some alphabet \(\Sigma\). A naming system for a finite set \(X\) is a partial surjective function \(\nu:\Sigma^*\to X\) taking concrete data to the mathematical entity it describes. Hence every object in \(X\) has at least one description or name, but this need not be unique, and not all words are valid names

  • e.g. \(\nu(\texttt{2/3})=\nu(\texttt{4/6})=\frac{2}{3}\), but \(\texttt{2/3/5}\) is not a valid name of a rational number.

Ariadne mainly deals with objects from uncountable sets, such as real numbers and continuous functions. It is impossible to find a description of objects from such sets for which objects are encoded by a finite amount of data. However, all the objects we study have continuum cardinality, and can be encoded by an infinite stream of (binary) data. Then a naming system or representation is a partial surjective function \(\mu:\Sigma^\omega \to X\).

  • e.g. \(\texttt{3.14159}\cdots\) is an initial segment of the name of \(\pi\) in decimal.

It is of course, impossible, to compute the complete name of an object. For this reason, it is important that we can extract useful information about an object from a finite prefix of the name.

  • e.g. Given \(\mu(\texttt{3.14159}\cdots)=p\), we know for sure that \(p\in[3.14159\!:\!3.14160]\).

Effective and Validated types

The relationship between infinite and finite data gives rise to one of the core conceptualisations in Ariadne, that of the kind of information. We have already seen Validated information, which is finite, and provides guarantees about the value of the object, without specifying it completely, and Effective information, which is infinite, but from which Validated information can be extracted. The amount of information which is extracted is given by a parameter Effort (this name may change in future). Hence we have a constructor Validated<T>::Validated(Effective<T>,Effort), or a function compute(Effective<T>, Effort) -> Validated<T> which performs the computation.

For a given type, there are many possible equivalent naming systems. For example, we could describe a real number using a binary or a decimal expansion (though it turns out that these are not quite equivalent, or even appropriate). Hence our Validated<T> is a generic class which can store a description in any such admissible representation. In order to use the computed information, we must be able to manipulate it in some concrete way. For number classes such as Validated<Real>, this is typically a therefore define for each type of mathematical object T, certain concrete classes which can be gotten from a Validated<T> using a getter method. For function types, this is typically a way of evaluating the function.

The information provided by a finite prefix of a name of an object does not specify the object exactly, but instead merely shows that the object lies in a restricted set of possibilities. For an admissible representation, this set is related to the topology of the represented space. Theoretically, we find a basic open subset containing the object, though for practical reasons, it is usually more convenient to take the closure (in a locally-compact Hausdorff space). Since different representations may correspond most naturally to different bases, our Validated types do not force a particular concrete description, but merely require that suitable information can be extracted e.g. DyadicBounds for a ValidatedReal number.

Although Validated information encodes sets of mathematical values, we do not conceptualised them as sets in Ariadne. For validated information represents partial knowledge about a single value, rather than describing a collections of values. For this reason, we do not provide set-theoretic operators such as subset tests and intersections, but predicates refines(Validated<T>,Validated<T>), inconsistent(Validated<T>,Validated<T>) and a refinement(Validated<T>,Validated<T>) operator. Note that the refines and inconsistent predicates check if they are definitely true, and may return false even when satisfied to provide faster checks.

The length of the information describing a Validated object provides an integer grading of information. We shall later see that it is convenient to sometimes provide more parameters (called properties) of an object controlling how the information is represented. (e.g. a polynomial approximation to a function may be controlled both by a precision of its coefficients, and the maximum degree of its terms.) It is also sometimes convenient to forget the length of information stored. (e.g. a decimal approximation 0.75000000 to a value may be truncated/simplified to 0.75.) The choice here affects the ability to estimate the amount of work that should be put in to computing an Effective object which is to be combined with a Validated object.

In some cases, rigorous bounds on a value are not needed, and we can use Approximate computation, which is usually faster. A common use-case for approximate computation is to precondition or hotstart a rigorous computation.

When specifying a problem, we may not even wish to specify which representations and algorithms to use, leaving this open for parametrisation. An object which is mathematically well-defined, but for which no computational content is specified, is Abstract, and will typically have a Symbolic description. e.g. 3*atan(sqrt(3)) defines a number, but requires concrete algorithms for sqrt and atan in order to compute.

Completion and Function types

There are two main ways of forming effective types in Ariadne, namely via completions and functions.

Completion Types

The completion construction can be applied to both metric and ordered types.

In the metric case, the class should provide a dist(...) function giving the metric, or support either taking abs(...) or norm(...), returning a positive upper bound. The metric completion is not the usual completion via Cauchy series, but use fast Cauchy sequences \((q_n)\) satisfying

\[ d(q_{n_1},q_{n_2}) \leq 2^{-\min(n_1,n_2)} . \]

In this way, if \(x_\infty = \lim_{n\to\infty} q_n\), then it is known that

\[ d(x_\infty,q_n) \leq 2^{-n} \]

or, equivalently,

\[ x_\infty \in B_{2^{-n}}(q_n) . \]

An alternative to using a fast Cauchy sequence is to give an error seqence \((e_n) \searrow 0\) and require

\[ d(q_{n_1},q_{n_2}) \leq e_{\min(n_1,n_2)} . \]

In the ordered case, there are directed completions, lower and upper, which denote the limit of a monotone sequence.

\[ q_{n+1} \geq q_n \text{ or } q_{n+1} \leq q_n \]

Combining both kinds of information gives a two-sided completion.

If no convergence rate is given, we obtain the naive completion. Although the sequence converges, no information about the limit can be obtained from any finite prefix of the sequence, so the naive completion is essentially useless! However, Approximate information is equivalent to Validated Naive information. For this reason, we one could include the naive completion to round off the type system.

Although these completion constructions can be defined in terms of limits of sequences of points, in Ariadne, we always consider the result as defining a (nested) sequence of sets, each of which contains the correct value. The types of these sets are Ball for metric space completions, Bounds for ordered completions, LowerBound and UpperBound for increasing and decreasing completions, and Approximation for the naive completion. These classes, along with (Exact)Value form the main kinds of concrete information in Ariadne.

When an Algebraic object supports a completion, this is indicated as the CompletionType.

Function Types

A function type Function is characterised by its signature, which in C++ has the form R(A0,A1,...), and is specified by its evaluation or call operator, ->R or evaluate(FunctionConcept<R(AS...)> f, AS...)

When the arguments of the function are completions, there is a canonical conversion (N.B. This statement needs to be checked to see if it holds in full generality) from Effective to Validated. For evaluating the function on an effective object requires computing information on the result from a finite amount of information on the argument. This means that an effective function maps Validated objects to Validated objects, so can also be seen as a Validated function.

Note that while both an EffectiveFunction<R(A)> and a ValidatedFunction<R(A)> are functions from Validated to Validated<R>, they also satisfy additional constraints on the image. A validated function \(\hat{f}\) should be monotone in the arguments i.e. \(\hat{x} \subset \hat{y} \Rightarrow \hat{f}(\hat{x})\subset\hat{f}(\hat{y})\), and an effective function \(f\) must also be convergent i.e. \(\bigcap_{n=0}^{\infty}\hat{x}_n=\{x\} \Rightarrow \bigcap_{n=0}^{\infty} f(\hat{x}_n) = \{f(x)\}\)

Ariadne also supports function classes with more information. Most (Continuous)Function objects can be evaluated on appropriate algebras, and DifferentiableFunction objects support differentiation. Further, PiecewiseContinuousFunction support restricted evaluation, and MeasurableFunction objects are defined in terms of (pre)images of sets, and do not support evaluation at all.

REMARK: We are in the process of refactoring the function classes, so the information gives details of future behaviour.

Product, union and sub-types

In addition to completion and function types, we can also define types as (cartesian) products, as disjoint unions, or as subtypes. In principle, this makes Ariadne's type system a Cartesian closed category, though in practice we do not support arbitrary higher-order types.

Concrete, Generic and Algebraic types

Computations in Ariadne are performed by classes which support efficient operations for the problem at hand. Each of these classes is a concrete model for a mathematical abstraction, such as a number, function, or set. The relationship between these Concrete and Generic types is defined as follows:

A Concrete object of class X has a ConcreteConcept::generic(...) method which returns GenericType<X>. Additionally, a concrete object may also be (explicity) converted to its generic type.

Usually the conversion will not be explicit, so a concrete object may be used whenever a generic is required.) From an object-oriented programming viewpoint, a concrete object is a subtype of its generic type, but as this may be difficult or inefficient to realise by subclassing, we do not require a subclassing relationship.

A concrete object is specified by its properties, which are given by the ConcreteConcept::properties() method. It is constructible from its GenericType and its PropertiesType as ConcreteConcept::ConcreteConcept(GenericType, PropertiesType) If the GenericType is default-constructible, then it is also constructible from its PropertiesType alone. Since after assignment, the properties are known, a concrete object is also assignable from its GenericType alone. Additionally, any binary operation between a concrete object and its generic type returns a concrete object, with the generic object first being cast to the concrete object:

op(Concrete x, GenericType<Concrete> y) { return op(x, Concrete(y,x.properties())); }

The PropertiesType may be a single class, or a Tuple of classes PRS... . In the latter case, whenever a Tuple<PRS...> is required as an argument, the individual properties may be substituted instead.

In general, Effective types will be Generic, and Concrete types will be Validated. The properties of a validated concrete object typically provide a grading of the representation, so can in principle be used instead of the Effort to specify the accuracy of a computation.

Exact and rounded operations

In Ariadne, core numerical types include Integer, Dyadic and Rational, supported by computation-oriented classes DoublePrecisionFloat and MultiplePrecisionFloat. The former are ExactTag or Algebraic classes, since they support exact operations, typically with an algebraic signature, but not analytic operations which require a completion. The floating-point numbers are RoundedTag or Concrete classes, and support rounded operations, based on the mathematical type the represent. Since these are primitive, countable data types, they support exact comparisons. However, this makes them dangerous in user code, so they should be wrapped in a Value, Ball, Bounds or Approximation for most work.

Rounded numeric types support rounding upward, downward, and to nearest. Further, since current processors support builtin rounded arithmetic only through a global processor rounding mode state, they also support a round argument, which rounds to the current global rounding mode. These rounding arguments are placed after the input values in a constructor e.g. FloatDP(Rational, RoundingModeType, PrecisionType), but as the first argument in an operator e.g. add(RoundingModeType, FloatDP, FloatDP). All rounded operations in Ariadne need a rounding specifier (though this is currently not strictly enforced).

Algebraic operations

Ariadne supports concepts for the algebraic classes of rings, fields, lattices, vectors, algebras and vectors of algebras. These support the usual mathematical operations, as detailed below. Further, elementary transcendental operations are supported for complete objects.

All operations are named. Where symbolic operators are traditionally used, such as + for add, a named version is also provided. An Algebra A has a NumericType X, and a Vector has a ScalarType. All types support assignment from an Integer.

The supported basic operations on numbers are as follows:

  • Ring X: neg(X)->X, add(X,X)->X, mul(X,X)->X; nul, pos, sub, sqr, pow.
  • Field X: neg(X)->X, rec(X)->X, add(X,X)->X, mul(X,X)->X; sub, div, hlf, sqr, pow.
  • Lattice X: max(X,X)->X, min(X,X)->X; also abs(x)->X if negation is supported.
  • Elementary X: sqrt(X)->X, exp(X)->X, log(X)->X, sin(X)->X, cos(X)->X, tan(X)->X, atan(X)->X.

The nul operator creates the zero element of the appropriate kind, pos creates a copy, sub(x1,x2)=add(x1,neg(x2)), sqr(x)=mul(x,x), div(x1,x2)=mul(x1,rec(x2)), hlf(x)=x/2, and abs(x)=max(x,neg(x)).

Additionally, Ariadne supports directed Lower and Upper numbers, which only support monotone operations, and Positive versions of all number types.

The neg, add, sqrt, exp, log atan, max and min operators are monotonic, and mul and rec are also monotonic on positive numbers. The add, mul, rec, sqrt and atan operators preserve positivity, sqr, exp and abs always yield positive answers, and sqrt and log require positive arguments. The max operator returns a positive value any of its arguments is positive, and min returns a positive value if all of its arguments are positive.

Algebraic types support the following arithmetic:

  • Vector V: neg(V)->V, add(V,V)->V, mul(V,X)->V; sub(V,V), mul(X,V), div(V,X), dot(V,V), norm(V)
  • Algebra A: neg(A)->A, add(A,A)->A, mul(A,A)->A, add(A,X)->A, mul(A,X)->A; sub(A,A) etc.
  • VectorAlgebra VA: neg(VA)->VA, add(VA,VA)->VA, add(VA,VX)->VA, mul(VA,A)->VA, mul(VA,X)->VA; etc

Additionally, a normed algebra has norm(A), and a graded algebra has A::degree(). A differential algebra DA has a derivative(DA, I) for some index type I. A function algebra supports coordinate constructors as well as constants.

For Concrete objects, all relevant concrete-generic mixed operations are supported.

Predicate and Set types

As well as numbers, Ariadne also supports logical types. The usual Boolean type is used for the result of a decidable predicate, and the Kleenean type for a quasidecidable predicate, which may be (provably) true or false, or of unknown or even unknowable truth indeterminate. The Sierpinskian represents the result of a predicate which cannot (robustly) be falsified, such as the apartness/inequality relation \(\neq\) on uncountable sets. The LowerKleenean type represents the result of a quasidecidable predicate which has only been checked for truth; for example, we may wish to prove the the maximum value of a function over a bounded interval is above some value, without spending the computational effort to provided a definitive result when this is not the case. Similarly, the UpperKleenean type represents the result of a quasidecidable predicate which has only been checked for falseness. The Effective versions of the logical types support a check(Effort) method which returns a Validated version.

Set types can be defined in terms of these predicates. The RegularSet<X> type (sometimes known as a complemented set) is defined by its elements

RegularSet<X>::contains(X)->Kleenean

(Note that our definition varies slightly from that commonly used in topology.) The lower type of the regular sets is the OpenSet<X> type, defined by a verifiable element test:

OpenSet<X>::contains(X)->LowerKleenean

The upper type is the CompactSet<X> type, defined by a falsifiable element test:

ClosedSet<X>::contains(X)->UpperKleenean

Regular, open and closed sets support intersection and union operations, and preimages under continuous functions.

The LocatedSet<X> type is defined by its intersection or subset relation with regular sets (equivalently, by its intersection and subset relation with openn sets) with
