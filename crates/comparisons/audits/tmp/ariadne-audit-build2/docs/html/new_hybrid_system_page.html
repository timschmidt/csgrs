Proposals for a Hybrid System Data Type (version 0.5)

An Ariadne hybrid system is a model of a deterministic or nondeterministic system with finitely many variables and finitely many possible events, but without stochastic or distributed (i.e. described by a partial diffferential equations) behaviour.

A hybrid system lives in a universe, the states of which are described by variables, and the transitions by real time and discrete actions.

  • A countable set of DiscreteEvents, each labelled by a valid String identifier.
  • A countable set of Variables, each labelled by a unique String identifier, and each with a type, which can be
    • DiscreteVariable: A quantity lying in a denumerable discrete topological space e.g EnumeratedVariable, IntegerVariable. Testing for equality of two values of a discrete variable must be a decidable operation.
    • ContinuousVariable: A quantity lying in a countably-based (connected) topological space e.g. RealVariable. Testing for equality of two values of a continuous variable is (typically) undecidable, though in most cases inequality is verifiable.

Initially, all possible behaviour is possible in the universe; variables can change arbitrarily, and actions can occur at any time with arbitrary updates. A system model is a finite set of Rules, which restrict the possible behaviour of the universe.

Rationale
The main rationale for defining systems by rules is that adding new rules can only restrict the behaviour of the system. This is vital for assume-guarantee reasoning. A secondary benefit it that the behaviour is independent of the order in which the rules are given.

Since Ariadne is a computational tool for analysing system evolution, the rules governing the system have to be intensional (defined using explicit assignments of variables) rather than extensional (defined by equations relating the variables). Since we wish to assign a rigorous computational semantics, all functions must be computable, in particular, all functions must be continuous. This means that a discrete variable can only (sensibly) be defined in terms of other discrete variables.

The main types of rules proposed for Ariadne are

  • Continuous assignments: p(q) -> xi=f(x1,...,xk)
  • Differential assignments: p(q) -> dot(xi)=f(x1,...,xk)
  • Invariant predicates: p(q) -> g(x1,...,xk)
  • Discrete updates: p(q) & s(e) -> next(qi)=u(qi,...,qk)
  • Continuous updates: p(q) & s(e) -> next(xi)=f(x1,...,xk)
  • Guard predicates: p(q) & s(e) -> g(x1,...,xk)

Each rule is valid given a predicate p(q) on the discrete state. Rules relating to action transitions are valid for single events.

Note that if no continuous or differential assignment is given to a continuous variable, then the value of that variable is arbitrary during time transitions. To ensure that a continuous variable remains constant, use dot(x) = 0 . Discrete variables cannot change during time transitions, so there is no need to provide a behaviour.

Note that the guard condition p(q) & s(e) \(\implies\) g(x1,...,xk) only implies a restriction on the conditions under which event e can occur if p(q) is true. For other states, the guard conditions places no restriction on when e can occur. Hence if e can only occur when e is true, then both the guard conditions p(q) & s(e) -> g(x) and ~p(q) & s(e) -> false need to be used.

Note that there is no default update for variables. During an action transition, if no next(x)= assignment is given, and no x= assignment is valid in the next discrete location, then the value of x is undefined. Hence if the value of x does not change during a discrete transition e in location q, then the predicate q & e -> next(x)=x needs to be used.

Note that since there is no variable hiding, any variable can be affected by any event. In order to make sure that a variable x can only change during events e1 and e2, then the condition ~{e1,e2} -> next(x)=x needs to be used. If x can never jump, then the condition next(x) = x should be used. In order to analyse a system, a rule of the form ~{e1,...,ek} -> next(x)=x needs to be given for all variables x. In other words, we need to specify the only events which can cause x to change.

Rationale
The rationale for providing explicit rules for constant and nonjumping variables is that otherwise one component may change the behaviour of another. For example, if a system has only rule dot(x)=a-x, and a were implicitly taken to be constant duing time transitions, then composing with the system dot(a)=-a would change the behaviour. This would make it impossible to use assume-guarantee reasoning.
Comparison with CIF
The Compositional Interchange Format (CIF) uses an operator NonJmp to declare a variable as nonjumping in an action transition unless it has already explicitly been declared as jumping. The advantage of using explicit rules is that the ordering of rules is immaterial, whereas the ordering of CIF operators is critical.
Explicit simple functions
It may be useful to add an explicit constant(x) operator as a shorthand for dot(x)=0, an explicit timer(x) for dot(x)=1 and an explicit nonjump(x) operator as a shorthand for next(x)=x. This could potentially be exploited in the solver routines.
Urgent actions
It might be useful to have explicit urgent actions, p(q) -> e <-> g(x1,...,xk) . The rationale is the same as the rationale in the HybridAutomaton class (Version 0.4); that for lower semantics we need to know when an invariant is the complement of a guard. Alternatively, it might be useful to have "may" and "must" guard predicates p(q) -> ( gmay(x1,...,xk) <- e <- gmust(x1,...,xk) )
More general rules
It might be useful to allow more general rules than those given above. For example, if an event e is only possible in discrete states p(q) and continuous states g(x), then it would be easier to write e -> p(q) & g(x) rather than p(q) & e -> g(x); ~p(q) & e -> false.
Variable bounds
It is almost certainly useful to be able to specify bounds on variables, such as p(q) -> -1 <= x <= 2 . This is useful in bounding inputs within differential equations.
Parallel composition
The parallel composition of two systems is formed by taking the conjunction of all rules i.e. the union of the two sets of rules. This means that composition is trivial to implement, and that it is trivial to check that it acts as a restriction on the behaviour of both subsystems!

Semantics and validity

Not all hybrid systems defined as a list of rules are valid system models. However, the situation is complicated since the model may be valid for some discrete states or discrete transitions, but not for others. We have the following validity rules:

  • A discrete state q is valid if
    • Every continuous variable y has exacly one defining equation
      • A continuous variable y defined by a differential equation dot(y)=f(x) is a continuous state variable
      • A continuous variable y defined by an algebraic equation y=f(x) is an auxiliary variable
    • There are no algebraic loops of assignments of algebraic variables.
  • A discrete transition e from a discrete state q is valid if
    • Every discrete variable q has exactly one defining update next(q)=r(p)
    • Every continuous variable y has exactly one defining equation, either
      • An update rule next(y)=r(x), or
      • An algebraic equation y=f(x) in the next discrete state next(q).

A system is overspecified if a variable has more than one defining rule in a given context. Since Ariadne requires intensional semantics for the continuous variables, evolution cannot proceed in a context where a continuous variable is overspecified, even if the assignments match. An overspecified discrete variable can in principle be handled, but is at best "bad practice" and we may decide to ban this as well.

A system is underspecified if a variable has no defining rule in a given context, and is used in that context. Systems with inputs are by their nature underspecified. An underspecified system can only be analysed in parallel with assumptions which give assignments (or constraints) for the undefined variables.

A system which has invalid discrete contexts can still be analysed if these contexts do not arise during the evolution. However, it is important to provide a static analysis of the system to find the contexts in which it is invalid.

Conversion to a Hybrid Automaton

In order to simulate or verify a hybrid system, the system description must contain enough information to be able to solve for all the variables of interest. In particular, we should be able to convert the description to a hybrid automaton, which is a constructive description of a hybrid system.

Since there may be some discrete valuations which naturally arise during modelling but do not correspond to valid discrete modes e.g. because some variable is overspecified, we construct a hybrid automaton from a set of initial discrete states. The automaton is statically valid if every discrete state reachable from an initial discrete state in the discrete abstraction of the hybrid system is valid.

We need the following definitions

  • Discrete states
    • A discrete valuation q' is a refinement of q if every variable qi occuring in q also occurs in q' and has the same value.
    • A set of discrete states is a set of valuations, none of which is a refinement of another.
  • Continuous variables For a discrete valuation q, a continuous variable xi is
    • A state variable if it is defined by a differential equation dot(xi)=f(x1,...,xk).
    • An output or auxiliary variable if it is defined by an algebraic equation xi=f(x1,...,xk).
    • An input variable if it is used in the description of a state or auxiliary variable, in a guard condition or in a reset relation, but is not defined by a differential or algebraic equation.
  • Trivial events An event e is trivial in discrete state q if either
    • the guard condition is the constant false, or
    • during a discrete transition, the discrete updates are of the form next(qi)=qi and the continuous resets are of the form next(xi)=xi.
    • Since no valuation may refine another, no extra discrete assignments are allowed.

A hybrid system is convertable to a hybrid automaton if the following conditions are satisfied.

  • State refinement It is not possible to reach a discrete valuation which is a refinement of another discrete valuation.
    • This condition is not strictly necessary, but it results in no loss of generality in the dynamics, and may help find modelling errors. Further, it means that the algorithm to convert to a hybrid automaton terminates if all discrete variables take on finitely many values.
  • State predicates Any discrete predicate p(q) is computable in any discrete state q.
  • No unbounded input variables In any discrete state, there are no input variables.
    • As a weaker condition (resulting in a nondeterministic automaton), we can require: No unbounded input variables In any discrete state, any input variable xi lies in a bounded interval [a,b].
  • Algebraic loops In a discrete state q, the graph giving the dependencies of the auxiliary variables must be acyclic.
    • This means that there is an order of computation of the auxiliary variables in which each only depends on already computed variables.
  • Guard conditions Every guard condition g(x1,...,xk) defined in a discrete state q may only use state and auxiliary variables.
  • Reset relations Every reset relation next(xi)=r(x1,...,xk) defined in a discrete state q, must either only use state and auxiliary variables in q, or the guard condition must be the constant false.
  • Transitions In every discrete transition, all the state variables in the new mode are specified by a reset, but none of the discrete variables are.
  • Finitely many events In a discrete state q, there can be only finitely many nontrivial discrete events.
    • This is required in order that the discrete automaton has only a finite number of arrows from any discrete state.

Note that in a subsystem i.e. a system which may be composed with others, there is a difference between an event with guard condition false and a guard with all resets of the form next(vi)=vi. In the former, the event cannot happen at all in any parallel composition, whereas in the latter, the event may happen, but just does not directly affect the state of the subsystem.

To convert a hybrid system to a hybrid automaton, we use the following algorithm:

  • For each new discrete valuation:
    • Check if the valuation is not a refinement of an existing valuation.
    • Extract the continuous state variables xi.
    • Solve for the output/auxiliary variables in terms of the state variables.
    • Substitute the auxiliary variables in terms of the state variables in the dynamic equations.
    • Substitute the auxiliary variables in terms of the state variables in the invariants.
    • Compute the set of nontrivial events and check that this is finite.
  • For each nontrivial event:
    • Compute the target discrete state. If this is new, insert in the set of uncomputed discrete states.
    • Substitute the auxiliary variables in terms of the state variables in the guard predicates.
    • Substitute the auxiliary variables in terms of the state variables in the reset equations.

The main difficulty is to test triviality, since it requires proving triviality for all but finitely many events. To do this, we use the fact that since the only atomic test allowed on the current event e is testing for equality with a constant event ei, every set of events is either computably finite or cofinite. It is simple to prove triviality for a cofinite set of events.

Example - A simple heating system

// Declare the hyrbid system object
HybridSystem system;
// Declare the events, types and variables
DiscreteEvent turn_on("turn_on");
DiscreteEvent turn_off("turn_off");
DiscreteEvent midnight("midnight");
DiscreteType swtch("Switch",(build_array,"on","off"));
DiscreteVariable heater("heater",swtch);
RealVariable T("T");
RealVariable t("t");
// Define the continuous dynamics
system.new_dynamic(heater=="on", dot(T)=20+cos(t));
system.new_dynamic(heater=="off", dot(T)=10+cos(t));
system.new_dynamic(dot(t)=1);
// Define the nontrivial update rules
system.new_reset(turn_off,heater=="on",next(heater)="off");
system.new_reset(turn_on,next(heater)=DiscreteValue("on"));
system.new_reset(midnight,next(t)=0.0);
// Define the guard sets and invariants
system.new_guard(turn_on,T<=16.0);
system.new_guard(turn_off,T>=22.0);
system.new_guard(midnight,t>=1.0);
system.new_invariant(T>=16.0);
system.new_invariant(T<=22.0);
system.new_invariant(t<=1.0);
// Define the trivial resets for nonjumping variables.
system.new_reset(next(T)=T);
system.new_reset(!midnight,next(t)=t);
