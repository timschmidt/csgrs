# CRCalc.js audit notes

- Repository pin: `ea5d92921599f3666c6afbf86235864e66469da9`.
- Inventory: 63 tracked files, 19,537 total lines. Core `cr.ts` (3,472) and `cr-test.mts` (173), all web TypeScript/config sources, and package/readme files were read in bounded numbered chunks. Generated distribution/static HTML, images, fonts, and other web assets are classified in the companion inventory because they contain no scalar implementation.
- Architecture: direct TypeScript port of AOSP/Boehm constructive reals. `CR` nodes expose precision-indexed BigInt approximations with one mutable per-node cached approximation; arithmetic is immutable lazy object composition. `slow_CR` batches precision requests. `BoundedRational` is a capped symbolic rational side channel (10,000-bit numerator+denominator budget, nullable on overflow). `UnifiedReal` stores a bounded-rational factor times a CR factor and recognizes a small identity table (`pi`, `e`, small square roots/logs) for exact simplification and decidable special-case comparisons.
- Strong ideas: explicit `PrecisionOverflowException` guard, error-budgeted operand precision for add/multiply, speculative cached precision for slow functions, AGM pi cache retaining intermediate square-root approximations, bounded symbolic side channel, and separate `definitely*`, approximate, and exact comparison APIs. These are conceptually relevant to Hyper's exactness/performance architecture, but Hyper already has stronger synchronized DAG caches and richer structural metadata.
- Exactness/termination risks: unbounded `CR.compareTo`/`signum` intentionally diverge on equality; `msd_get` does likewise for zero. `select_CR` chooses a branch from a coarse `get_appr(-20)` sign and then permanently caches that choice, so custom approximation providers with a near-zero result can violate exact branch semantics. `UnifiedReal.approxEquals` explicitly permits false equality within tolerance. `pow` and factorial use documented arbitrary limits/heuristics. Hyper's explicit indeterminate/domain outcomes are preferable.
- Concrete source issue: `UnifiedReal.asin` condition at lines 3052-3054 uses `||` between mutually exclusive `!==` tests, so it is always true; the intended branch guard is likely `&&`. Existing `asinNonHalves` still catches key half-square-root cases, so no safe Hyper transfer follows.
- Memory/performance: browser worker keeps many unbounded `Map` caches keyed by object identity, including nested binary maps; no eviction or size cap exists. Equal-but-distinct UnifiedReal expressions miss these caches. CR node caches are mutable and not thread-shared (worker isolation), while Hyper's synchronized shared caches require stronger ownership discipline. Taylor-series elementary functions are simple but potentially slow; pi AGM retains all `b[n]` approximations.
- Web integration: precision is requested incrementally (32-bit initial, 128-bit steps, demand-driven scrolling) and stale worker results are rejected by monotonically increasing UIDs. UI guards large output and offers exact/truncated distinction. This demand scheduling is a useful product-level pattern but not a scalar-core transfer.
- Tests: checked-in distribution test `node crcalc-js/dist/cr-test.mjs` passed (`Success`). Native `npm test` could not rebuild because `terser` is absent. Tests are one monolithic sanity sequence with approximate comparisons and do not cover cache eviction, custom CR providers, exact equality divergence, parser fuzzing, negative/zero pow semantics, worker concurrency, or the asin guard.
- Hyper transfer decision: no production change selected. Retain as audit evidence only; the worthwhile concepts (bounded symbolic factor, explicit exact-vs-approximate comparison contracts, precision-overflow guards, demand-driven UI scheduling) are already represented or would need a deliberate Hyper design, while the mutable coarse branch/cache behavior is weaker than Hyper.
