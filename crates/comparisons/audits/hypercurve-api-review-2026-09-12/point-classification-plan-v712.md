# One exact point classification API

Current public CurveRegion2 classification accepts scalar-coordinate Point2 or, through a separate method, one selected algebraic image. CurvePath2 accepts only Point2. Generic CurvePoint2 already carries generated chord, circle, parallel, similarity and lazy endpoint evidence. Private retained-loop and Boolean probe classification can consume that carrier, but its public classification capability is split by representation.

First qualify the existing retained-loop authority on independent exact rectangle inside/outside/boundary/vertex oracles with nonmaterialized chord-normal, analytic-parallel, similarity and lazy-endpoint point constructions. This is an isolated copied-source probe, not a demonstrated kernel failure or production API change. Reuse certified native/one-field query paths; do not route ordinary points through heavyweight geometric probes.

Then migrate public region/path classify_point to &CurvePoint2 and region classify_points to &[CurvePoint2], remove public classify_algebraic_point, and update controlled callers directly without borrowed view types, compatibility aliases or conversion-only overloads. Preserve private specialized scalar/algebraic kernels where they have distinct arithmetic contracts. Keep indexed native batch work shared and avoid materializing selected coordinate images. Mixed exact batches should preserve input order and the same certainty upgrade rules.

Before implementation, verify the private Boolean probe's FilledRegion mode honors regularized boundary ownership, while LoopParity remains exclusively the nesting predicate. A public arbitrary point must still detect boundary endpoints, overlaps and degeneracies; do not assume an off-boundary precondition from a helper name. Extend verification to nested islands/holes, generated boundary points and operation-produced regions. Prototype alone is not sufficient for the migration.

Found during this audit: try_from_native_boundary_contours_borrowed is another direct to_vec forwarding shim. Remove it with its callers in a separate coherent change if not already consumed by the classification migration. No production edits yet. NextV713 probe.

Source follow-up: CurveRegionBooleanContext::try_new_curve_boundary(&[], region, policy) already prepares only the boundary carriers and no cross-operand pairs. Its existing FilledRegion probe mode uses retained filled sides and detects target-boundary contacts, so it may support a whole-region point query without a new context owner or duplicate arrangement build. Confirm that empty regions return Outside before any owner index is used. LoopParity remains distinct for nesting/path parity.

Native batch preservation can borrow the existing RegionQuery2 directly once and classify Cartesian members of &[CurvePoint2] through it; generated members retain common exact fallback. This avoids building a temporary Cartesian point vector or weakening selected evidence. Do not add a PointRef compatibility type or generic overload solely to preserve old call syntax.

Critical path semantics: CurvePath2::classify_point classifies the closed traversal's trace and even-odd interior. A retraced zero-area closed path still has boundary points, even when regularizing it as a two-dimensional region would erase it. Do NOT implement generated-point path queries by publicly constructing/regularizing CurveRegion2. Reuse the private raw boundary-loop/LoopParity authority and include a generated point on a closed retraced path as a regression. Full-region probes use FilledRegion and the published canonical boundary, keeping winding/ownership semantics distinct.

For region batches, reuse RegionQuery2 once for Cartesian members rather than projecting all general points into a temporary Point2 vector. Lazily retain a successful CurveRegionBooleanContext::try_new_curve_boundary(&[], region, policy) within the operation for generated members; initialize per policy attempt, never cache an unsuccessful preparation as permanent absence. Native and one-field scalar kernels should remain demand-driven. A shared private point dispatcher can accept this local preparation slot; no public borrowed view type, generic compatibility facade, or forwarding overload is needed.

Potential additional completeness issue to investigate, not yet demonstrated: the old native batch shortcut returns its indexed classifications immediately, whereas scalar classify_point_raw falls back to retained winding when the native specialization is uncertain. Ensure the unified batch preserves this fallback, with a concrete independent fixture before claiming a repair.
